## Lecture

### 1. The structure of a .NET project

A .NET project contains source code and configuration that tell the .NET SDK how to build an application or library.

A basic console project created with `dotnet new console` typically contains:

```text
02-ProjectStructureAndConfiguration/
├── 02-ProjectStructureAndConfiguration.csproj
├── Program.cs
├── obj/
└── bin/
```

Each part serves a different purpose:

- **`.csproj`** — Defines the project configuration, target framework, build properties, and dependencies.
- **`Program.cs`** — Contains the C# source code for the application.
- **`obj/`** — Stores intermediate build files, generated source files, and restore metadata.
- **`bin/`** — Contains compiled build output, including the application assembly and other runtime files.

The `obj/` and `bin/` directories are generated by .NET commands. They generally should not be committed to Git because they can be regenerated.

The `.csproj` file is especially important because it describes how the source code should be built. Two projects can contain similar C# code but produce different results because their project configurations differ.

### 2. The `.csproj` file

Modern .NET projects use the SDK-style project format. A basic console application's project file may look like this:

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

The root `Project` element specifies which SDK should build the project. `Microsoft.NET.Sdk` is the standard SDK for ordinary .NET applications and libraries.

The `PropertyGroup` contains settings that control the build.

- `OutputType` determines whether the project produces an executable application or a library.
- `TargetFramework` specifies the .NET framework version targeted by the project.
- `ImplicitUsings` controls whether the SDK automatically includes common namespace imports.
- `Nullable` controls nullable reference type analysis and related compiler behavior.

These settings are not C# statements. They are XML configuration interpreted by the build system.

You can inspect your current project file directly or print it from the terminal:

```bash
cat 02-ProjectStructureAndConfiguration.csproj
```

The actual values may differ depending on the installed SDK, project template, and any changes you have made.

### 3. Target frameworks and TFMs

The `TargetFramework` property identifies the framework that a project targets.

For example:

```xml
<TargetFramework>net10.0</TargetFramework>
```

`net10.0` is a **target framework moniker (TFM)** for .NET 10. It tells the SDK which framework reference assemblies, APIs, and compatibility rules to use when building the project.

The target framework is distinct from the SDK version. The SDK supplies tools for restoring, compiling, testing, and publishing projects. The target framework specifies the platform and API surface the project is built against.

You can inspect the installed SDK versions with:

```bash
dotnet --list-sdks
```

You can inspect installed runtimes with:

```bash
dotnet --list-runtimes
```

These commands report different things. An SDK includes development tools; a runtime provides the components needed to execute applications that depend on it.

Having a particular SDK installed does not mean every possible target framework is available. The SDK may need to download reference packs or other components during restore or build.

A project targeting `net10.0` does not automatically target older .NET versions. If you need to support multiple target frameworks, a project can use `TargetFrameworks`:

```xml
<PropertyGroup>
  <TargetFrameworks>net9.0;net10.0</TargetFrameworks>
</PropertyGroup>
```

This is called multi-targeting. Each target framework is built separately, and the code must be compatible with each target. Do not add multi-targeting unless you actually need to support multiple frameworks.

For this learning project, keep the target framework generated by your installed .NET SDK unless a module explicitly requires a change.

### 4. Output type: executable or library

The `OutputType` property determines the kind of output produced by the project.

```xml
<OutputType>Exe</OutputType>
```

`Exe` identifies an executable application. A console application can be run using `dotnet run`.

A reusable class library generally uses:

```xml
<OutputType>Library</OutputType>
```

A library contains reusable types and functionality rather than being an application intended to run directly. Other projects can reference it.

In SDK-style projects, omitting `OutputType` normally produces a library. Console templates explicitly set it to `Exe`.

For example, a future Boids application might separate reusable simulation logic into a library and use a separate application project to display or host the simulation. The library would contain the simulation types, while the application would provide the entry point and user interface.

### 5. Implicit usings and namespaces

C# namespaces organize types and prevent naming conflicts. To use a type from another namespace, source code often includes a `using` directive.

For example:

```csharp
using System;
using System.Collections.Generic;

Console.WriteLine("Hello, World!");

List<int> counts = new() { 10, 20, 30 };
```

The `System` namespace contains types such as `Console`, while `System.Collections.Generic` contains types such as `List<T>` and `Dictionary<TKey, TValue>`.

When the project contains:

```xml
<ImplicitUsings>enable</ImplicitUsings>
```

the SDK supplies common global using directives for the project's type of application. That is why a modern console template can often use `Console.WriteLine` and `List<T>` without explicitly importing their namespaces.

You can disable implicit usings and write the required `using` directives yourself, but doing so is not necessary for this module.

A global using directive applies across source files in the project. A regular using directive applies only to the source file where it appears.

The important distinction is that implicit usings affect which namespaces are available to your source code. They do not automatically add arbitrary external packages or make every type in .NET available without qualification.

### 6. Nullable reference types

The project property:

```xml
<Nullable>enable</Nullable>
```

enables nullable reference type analysis.

Reference types such as `string` can represent references to objects, and a reference can also be `null`. Nullable reference type annotations let you communicate whether `null` is expected.

```csharp
string name = "Boids";
string? optionalName = null;
```

Here, `string` indicates that `name` is intended to hold a non-null string, while `string?` indicates that `optionalName` may hold `null`.

With nullable analysis enabled, the compiler warns about many potential null-related mistakes. For example:

```csharp
string? simulationName = null;

// The compiler warns because simulationName may be null.
Console.WriteLine(simulationName.Length);
```

You can handle the possibility of `null` explicitly:

```csharp
if (simulationName is not null)
{
    Console.WriteLine(simulationName.Length);
}
```

Nullable reference types primarily provide compile-time analysis and warnings. They do not automatically make reference types non-null at runtime, nor do they eliminate every possible null-related error.

The nullable annotation also differs from nullable value types. For example, `int?` is shorthand for `Nullable<int>` and represents a value type that can contain an integer or no value.

Keep nullable analysis enabled for these learning projects. It helps identify potential problems before the application runs.

### 7. Build properties and compiler settings

The `.csproj` file can contain many other properties that control compilation.

For example:

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <ImplicitUsings>enable</ImplicitUsings>
  <Nullable>enable</Nullable>
  <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
</PropertyGroup>
```

`TreatWarningsAsErrors` controls whether compiler warnings are treated as errors. Setting it to `true` can enforce stricter standards, but it may also prevent a build when warnings remain.

Other properties can control language versions, output paths, assembly names, documentation generation, and conditional compilation.

Avoid adding properties simply because they exist. Each setting should solve a specific problem or enforce a deliberate project standard.

For this module, inspect the settings already present before changing them. The goal is to understand what the configuration does, not to accumulate unnecessary build options.

### 8. Debug and Release configurations

.NET projects commonly use two build configurations:

- **Debug** — Intended for development and debugging, typically retaining debugging information and avoiding some optimizations.
- **Release** — Intended for production-oriented builds, typically enabling optimizations.

Build using Debug:

```bash
dotnet build --configuration Debug
```

Build using Release:

```bash
dotnet build --configuration Release
```

The output is normally placed in separate directories:

```text
bin/
├── Debug/
│   └── net10.0/
└── Release/
    └── net10.0/
```

The exact output layout can vary with the project configuration and SDK.

You can run the project using a selected configuration:

```bash
dotnet run --configuration Debug
```

```bash
dotnet run --configuration Release
```

The configuration does not change the basic purpose of the source code. It changes how the build is performed. Release builds are not automatically production-ready: publishing, configuration, deployment requirements, and testing still matter.

### 9. Project references

A project can reference another project to use its public types. This is useful when separating reusable logic from an application.

Imagine the following structure:

```text
MySolution/
├── SimulationApp/
│   └── SimulationApp.csproj
└── SimulationCore/
    └── SimulationCore.csproj
```

`SimulationCore` might contain a `Boid` class, while `SimulationApp` uses that class to run the simulation.

A project reference can be added with:

```bash
dotnet add SimulationApp/SimulationApp.csproj reference SimulationCore/SimulationCore.csproj
```

The paths are relative to the directory where the command runs.

A project reference is different from a NuGet package reference. A project reference connects one project to another project in your source tree. A package reference uses a package distributed through a package source, usually NuGet.

When building a project with project references, the build system resolves the dependency and builds the required referenced projects as needed.

Do not create an additional library solely to practice project references if the current module does not require it. The example illustrates how projects can be connected when a real design calls for separation.

### 10. Solutions and projects

A **project** describes one buildable unit, such as a console application or class library. It normally has a `.csproj` file.

A **solution** groups related projects so they can be managed and built together. A solution file typically uses the `.sln` or newer `.slnx` format, depending on how it was created.

For example:

```text
DotNetLearning/
└── 02-dotnet-fundamentals/
    ├── 01-DotNetPlatformAndRuntime/
    │   └── 01-DotNetPlatformAndRuntime.csproj
    ├── 02-ProjectStructureAndConfiguration/
    │   └── 02-ProjectStructureAndConfiguration.csproj
    └── DotNetFundamentals.sln
```

The solution groups the projects, but each project retains its own source files and configuration.

You can create a solution with:

```bash
dotnet new sln -n DotNetFundamentals
```

You can add a project to the solution with:

```bash
dotnet sln DotNetFundamentals.sln add \
  01-DotNetPlatformAndRuntime/01-DotNetPlatformAndRuntime.csproj
```

The exact solution filename depends on the format and SDK tooling used. Use the filename that actually exists in your directory.

A solution is useful when you want to build or manage several related projects together. It is not required for every project, and creating a solution does not merge their source code into one project.

### 11. Configuration files versus project configuration

The `.csproj` file controls how the application is built. It is not the same as application configuration used while the program runs.

For example, a project file may specify the target framework and package references, while an `appsettings.json` file may hold application settings such as a logging level or a simulation's initial parameters.

A simple application settings file might look like this:

```json
{
  "Simulation": {
    "InitialBoidCount": 100,
    "MovementSpeed": 2.5
  }
}
```

This JSON file is only data. The application must use an appropriate configuration provider or code to read it. A plain console application does not necessarily load `appsettings.json` automatically.

ASP.NET Core applications commonly use a built-in configuration system that loads JSON files, environment variables, and other providers. You will study that system in the configuration module.

Do not place secrets such as passwords or API keys directly in a committed configuration file. Configuration should be managed according to the sensitivity and deployment needs of the application.

### 12. Inspecting and verifying a project

The .NET CLI provides commands for inspecting and validating project configuration.

From a project directory, you can run:

```bash
dotnet restore
```

This restores the dependencies required by the project.

```bash
dotnet build
```

This compiles the project and reports errors and warnings.

```bash
dotnet run
```

This builds and runs the application.

You can also query evaluated MSBuild properties:

```bash
dotnet msbuild -getProperty:TargetFramework
```

This prints the evaluated target framework property. You can inspect other properties similarly, for example:

```bash
dotnet msbuild -getProperty:OutputType
```

The evaluated values may be influenced by imported build files, SDK defaults, conditions, and command-line properties. The `.csproj` is the main place to start, but it is not necessarily the only source of build configuration.

A reliable workflow is to inspect the project file, make one deliberate change, build the project, and verify the result. If a change causes unexpected behavior, restore the original value and build again.
